# Agent judgments

Status: built 2026-09-19 under Joseph B's rulings R-J1 to R-J7 (recorded in the private research tier). Additive schema change: two new tables, one new module, and judgment writes inside two existing lanes. Humans decide; AI recommends. No function that writes a judgment changes a task, an evidence draft, or a review decision.

## Why one table

Before this change AI judgments sat at three grains in three places. The `agent_reviews` table holds one recommendation per evidence draft with source-level checks. The `agent_intake_receipts` table keeps per-claim checks inside `bundle_json`, unindexed. The first-pass archive keeps research as local files with no Convex reference. None answers a question such as "how often does this model's support verdict agree with the reviewer's decision on claims of this type". A single append-only table at claim grain, `agent_judgments`, answers it.

## What a judgment is

A judgment is an evaluative output about a subject: whether a source supports a claim, a recommendation on a draft, a status assessment for a place, an annotation that qualifies or disputes a claim, a duplicate or location verdict. A claim is a proposal of evidence and stays in the dossier or evidence record; a judgment refers to it by `claim_id` within a content hash. The evidence record stays immutable and judgments accumulate around it.

## The `agent_judgments` table

One row per judgment, written once, never patched. `judgment_id` is the SHA-256 of the canonical JSON envelope (`agent-judgment.v1`), so an identical retried write collapses onto one row and a re-judgment in a later batch appends a new row.

| Field | Content |
| --- | --- |
| `subject_kind`, `subject_ref` | `claim` (`<sha256>#<claim_id>`), `evidence_draft` (draft id), `evidence_version` (object hash), `first_pass` (sha256, reserved for the first-pass receipt), or `place` (`place_ref`). |
| `judgment_kind` | `claim_support`, `recommendation`, `status_assessment`, `annotation`, `duplicate`, `location`, and from v1.1 `registration_confidence`. |
| `outcome` | Fixed vocabulary per kind in `convex/lib/agentJudgments.ts` (`OUTCOMES_BY_KIND`); the writer refuses a mismatch. |
| `facet` | Optional discriminator between sibling judgments by one lane on one subject, for example the batch reviewer's `existence`, `date_support` and `location_plausibility` checks. |
| `confidence`, `access_method`, `source_locator`, `basis_note` | Optional. `access_method` is one of `opened`, `search_snippet`, `http_fetch`, `model_assessment`, `not_checked`. |
| `judge` | `agent_name`, `model_provider`, `model_requested`, `model_reported` or `model_unreported_reason` (exactly one), `prompt_version`, optional `code_revision` and `instruction_sha256`. From v1.1 also optional `kind` (`model` or `deterministic`), `standard_version` and `signal_vector_sha256`; a deterministic judge carries no model fields (see below). |
| `run` | `batch_id` or `agent_run_id`, `attempt`, `cost_usd` and `cost_basis`. An unknown, unmetered or no-model-call cost stays absent; it is never zero. A metered basis requires a value. |
| `context` | Optional `task_id`, `evidence_draft_id`, `evidence_version_hash`; required `place_ref` and `country_code`. |
| `score` | From v1.1, optional: the deterministic scorer's numbers and fired signals (see below). Part of the id envelope when present. |
| `parents` | The lane's earlier judgments of the same kind, facet and source on the same subject, newest first, at most ten. |
| `actor_user_id`, `ai_generated: true`, `created_at` | As in `agent_reviews`. |

Indexes: by judgment id, and by subject, task, batch and prompt version, each followed by `created_at` so a bounded read walks newest first and a cap drops the oldest rows; and `by_lineage` (subject, kind, judge, facet, source, `created_at`), which the writer uses to find a re-judgment's parents.

## The `judgment_dispositions` table

What a person did with one judgment: `judgment_id`, `reviewer_user_id`, `disposition` (`agreed`, `disagreed`, `corrected`, `not_considered`), an optional note that becomes required for a disagreement or correction, an optional `review_decision_id`, and `created_at`. Append-only. The `review_decisions` table keeps its draft-level `agent_review_id` and `agent_review_agreement` fields and its version-0 and version-1 hash contracts unchanged.

## Writers

`convex/lib/agentJudgments.recordJudgments` is the one write path. It validates each input, computes the id, returns an existing row unchanged, computes parents, and inserts. It accepts at most 100 judgments per call. The parent lookup reads the `by_lineage` index (subject, kind, judge, facet, source, newest first) and takes at most ten rows, so it stays bounded however many judgments other lanes have written about the subject; before 2026-09-24 it collected every judgment on the subject.

The Claude batch-review lane (`claudeReviews.recordArtifact`) writes one `recommendation` judgment for the draft and one `claim_support` judgment per recorded source check, in the same transaction as the `agent_reviews` artifact. The subject is the draft's newest evidence version when one exists, else the draft. The lane records the requested model and states that the response model id is not captured.

The internal bundle intake (`internalAgentIntake.ingestBundle`) writes one `claim_support` judgment per advisory `claim_checks` entry with its real `access_method`, one `recommendation` judgment on the intake evidence version, and one `status_assessment` judgment for the place from the researcher's dossier. The source-level `sources_checked` summary on the `agent_reviews` row now records `not_checked` when the reviewer did not check the source and `model_assessment` otherwise, and names the source rather than the claim id; the earlier row asserted an `existence` check by `model_assessment` for every claim.

The first-pass receipt ingest (`firstPassReceipts.ingestFirstPass`, added 2026-09-24) writes one `status_assessment` judgment for the place, attributed entirely from the dossier's run manifest (`<provider>-first-pass-researcher`) and keyed on that run, so passes carrying the same dossier share it; and one `annotation` judgment per claim annotation, attributed from the record's own attribution (`first-pass-annotator`, or `<provider>-first-pass-annotator` when the attribution names the dossier's run), whose subject is `<first-pass sha256>#<claim_id>` and whose `facet` numbers the annotation so sibling annotations on one claim are not read as revisions of each other. A record without a dossier yields no judgments. The claims stay in the record. See [revisitable agent research](agent-first-passes.md#receipts-in-the-shared-backend).

## Reads and the human disposition

`agentJudgments.listJudgmentsForTask`, `listJudgmentsForSubject` and `listDispositionsForJudgment` return newest first to reviewers, curators, administrators and the PI. `agentJudgments.recordJudgmentDisposition` appends one disposition; it refuses an unknown judgment, an unknown review decision, a decision about a different task or evidence draft from the judgment, and a disagreement or correction without a note of at least eight characters.

## agent-judgment.v1.1 (2026-10-01)

Version 1.1 widens version 1 so that a deterministic scorer can record its output beside model judgments. It narrows nothing, renames nothing and migrates nothing. Version 1 stays the default: a writer that sends no `schema_version` writes `agent-judgment.v1` and its ids are unchanged (`canonicalJson` drops absent keys; a regression test pins the id of the reference input). The writers in `claudeReviews`, `internalAgentIntake` and `firstPassReceipts` are untouched.

- **Judge.** `judge.kind` is `model` (the default) or `deterministic`. `judge.standard_version` (`confidence-standard/<major>.<minor>.<patch>`) is required on every v1.1 row of either kind, so a row names the standard it was made under. `judge.signal_vector_sha256` names the hash of the signal-vector file a deterministic judgment was computed from; it is a new field, and `instruction_sha256` keeps its meaning (the hash of a model's instruction text) and is never reused. `model_provider` and `model_requested` become optional in the validators; the validation function still requires them of a model judge.
- **Deterministic judge.** It requires v1.1, a non-empty `code_revision`, a 64-hex `signal_vector_sha256`, `run.cost_basis = no_model_call` and a `score` block. It carries no model fields, `instruction_sha256`, `access_method` or categorical `confidence`. `prompt_version` names the scorer configuration version. A model judge carries no `score` and no `no_model_call` basis.
- **Cost basis.** `no_model_call` joins the cost bases. A deterministic pass bills no vendor, so its cost stays absent, like an unknown cost.
- **Kind.** `registration_confidence` has the outcomes `screened`, `review` and `escalate`, the provisional tier of the confidence standard. No tier accepts: the tier orders the review queue and decides nothing. The identity and denomination components have no kind of their own and live in the score block.
- **Score block.** `edition_id`; `composite`; the four `components` (identity, location, status, denomination); `tier`, `tier_reasons` and `tier_pending`; the three `cut_points`; `calibrated`; `signals_fired` (term names per component, from the scorer configuration's closed vocabulary); `signal_values`; and `indicators`. Every number is finite and in [0, 1] (components, composite, cut points), every term matches `[a-z0-9_.]{1,64}` with at most 40 per array, and for a `registration_confidence` row the tier equals the outcome. `signal_values` holds only numeric and boolean signals from the fixed allowlist `SCORER_SIGNAL_VALUE_KEYS`, each with its own domain (a flag is a boolean or null; a count or measure is a bounded non-negative number or null) (tag completeness and counts, the `has_*` flags, footprint area, building and node-context flags, edit-history counts and ages, lifecycle flags, duplicate-risk counts and the cross-source match count). No string-valued signal is copied: names, editors, check dates, scripts and partner references stay in the signal vectors.
- **Component outcomes.** The converter writes a `status_assessment` row (facet `status`, outcome `unknown`), a `location` row (facet `location`, outcome `unclear`) and, where the duplicate indicator is set, a `duplicate` row (facet `duplicate`, outcome `unclear`). These are the vocabulary's non-committal values on purpose: the ruled cut points (composite 0.9 and 0.6, component floor 0.7) are a review trigger, and nothing ruled says that an uncalibrated status of 0.69 means likely inactive or a location of 0.69 means implausible. The numeric values and fired signals are in each row's score block, and the rows exist so a reviewer can dispose of each component separately. A ruled mapping can later write revised rows through lineage. Categorical `confidence` is omitted for the same reason. The adopted confidence standard (0.3.1, `docs/confidence-standard.md`) describes these rows as each carrying a categorical confidence; this implementation omits it, and reconciling the standard needs a revision ruled by the project lead.
- **Scorer rows.** `convex/lib/scorerJudgments.ts` holds the strict validator shared by the converter and the ingest, and a closed Convex validator for the ingest argument. A scorer row is about an OSM place (`osm:<node|way|relation>/<id>`), names the same place in its context, names no task, draft or evidence version, no batch id and no cost value, uses the agent name `osm-confidence-scorer`, pairs each kind with its facet, is attempt 1, and has exact formats for the scorer version (`p<n>-heuristic-<x.y.z>`), the 40-digit code revision, the edition id and the run id (`osm-confidence:<edition>:<vector hash prefix>:<converter version>`). Every fired signal, tier reason, pending condition and conflict reason must be a term from the scorer configuration's closed vocabulary listed in that file, so a row can carry only names the scorer defines. The basis note is generated from the row's own validated fields (`scorerBasisNote`) and the validator requires exactly that text, so no free text, and no personal detail, can reach a stored scorer row. The score's edition must lie in the context's country. The standalone validator checks the whole input against the closed ingest argument validator at every level, so an unknown key or a wrongly typed value is refused whoever calls it.
- **Lineage.** `by_lineage` is untouched. A scorer row has a stable agent name and facet and no source locator, so re-scoring a feature under a new signal-vector file appends a row whose `parents` name the earlier score, and an identical rerun collapses onto one row.
- **Converter.** `scripts/osm_confidence_judgments.mjs` reads a signal-vector file and its data manifest, checks the file's hash and every scorer field against the manifest, and writes a dry-run JSON file of batches of at most 100 rows plus the judgment ids. It talks to no backend. The committed fixture under `schemas/fixtures/agent-judgment-v1-1/` is synthetic; `--check` regenerates it in CI. The real vectors stay in the private tier.
- **Ingest.** `agentJudgments:ingestDeterministicJudgments` is an internal mutation behind `POW_INTERNAL_AGENT_INGEST_ENABLED=true`, attributed to the internal agent service user. It takes at most 100 rows that share the call's signal-vector hash and one country, validates each with the strict validator and writes them through `recordJudgments`. Running it against a deployment is a data import and needs the project lead's instruction; adding the function is not.
- **Reads.** `agentJudgments:listJudgmentsForTaskPlace` returns the judgments about the place a task is about, with each row's newest dispositions embedded, for the reviewer, curator, administrator and PI roles. The reviewer portal's panel is built on it; the RA portal shows no scorer output.

## Deployment

The change is additive: two new tables, one new module, new optional writes inside two existing mutations. It deploys from the reviewed head under the closure procedure in `AGENTS.md`. A reviewer panel that shows judgments per claim and records dispositions is the next step. The v1.1 change of 2026-10-01 is also additive: new optional fields, a widened version union, one new kind and cost basis, one new query and one new internal mutation.
