# Frozen Exports: Byte-Level Freezing And Bundle Verification

**Status:** Implemented 2026-09-12 as step two of D20 (`DECISIONS.md`, PI ruling 2026-09-11). Step one, the intake gate and snapshot-linked acceptance, is documented in [evidence-versions.md](evidence-versions.md) and merged as PR #111. Proposal pinning (step three) and portal restoration controls (step four) remain later steps. PR L1 of the [lean-storage brief](lean-storage-brief-2026-09-12.md) (D20 step two-b, rulings 1, 2, 3 and 12 of 2026-09-24) adds budgeted batch composition, export runs frozen by a scheduled chain, and gzip-compressed stored files; see [Budgeted batches and export runs](#budgeted-batches-and-export-runs-pr-l1) and [Stored encoding](#stored-encoding-pr-l1). The bundle contract is unchanged, and the committed fixture is byte-identical.

## The problem this closes

Before this change, `exports:freezeExportBatch` set `status: "frozen"` and marked every included task `exported` without capturing any bytes; `exports:getExportBundle` rebuilt the bundle from the current rows on every call. A "frozen" batch was a label over mutable content: a reopen, a reviewer edit, or an occupancy retirement after the freeze silently changed what the next retrieval returned. Freezing now rechecks eligibility and pinned versions at freeze time, captures the complete bundle including the confirmed locations actually approved, durably stores and verifies its bytes, and only then marks the batch frozen; withdrawal or supersession afterwards preserves those bytes while stopping further authorised processing.

## The bundle contract `pow-export-bundle.v1`

A bundle is a set of files plus one manifest, `export_manifest.json`. Every file is UTF-8 text. The manifest is written as `JSON.stringify(manifest, null, 2) + "\n"` and includes its own `manifest_hash`:

```json
{
  "bundle_contract": "pow-export-bundle.v1",
  "hash_contract": "pow-object.v1",
  "export_batch_id": "vu-convex-export-1789000000000",
  "country_code": "VU",
  "schema_version": "convex-task-layer.v0.1",
  "export_format": "bundle",
  "created_at": 1789000000000,
  "frozen_at": 1789000060000,
  "supersedes_export_batch_id": "vu-convex-export-1788000000000",
  "included_task_ids": ["..."],
  "included_review_decision_ids": ["..."],
  "included_acceptance_ids": ["..."],
  "included_task_count": 1,
  "included_evidence_count": 1,
  "included_historical_claim_count": 0,
  "included_review_decision_count": 1,
  "evidence_version_hashes": ["sha256:..."],
  "review_snapshot_hashes": ["sha256:..."],
  "files": [
    { "filename": "derived_state_events.jsonl", "content_type": "application/x-ndjson", "record_count": 3, "sha256": "<64 hex>", "byte_length": 812 },
    { "filename": "site_evidence_wide.csv", "content_type": "text/csv", "record_count": 1, "field_count": 90, "field_list_mismatch_count": 0, "sha256": "<64 hex>", "byte_length": 2048 }
  ],
  "manifest_hash": "sha256:<64 hex>"
}
```

- `manifest_hash` is `objectHash` (`pow-object.v1`: SHA-256 over the `pow-canonical-json.v1` bytes, RFC 8785) of the manifest object with the `manifest_hash` member omitted. Every other member is covered.
- `files` is sorted by `filename` (byte order) and lists every file in the bundle except `export_manifest.json` itself. `sha256` is the lower-case hex digest (no prefix) of the file's exact UTF-8 bytes; `byte_length` is the UTF-8 byte count (`new TextEncoder().encode(text).length`, never the ECMAScript string length). `record_count` is the number of JSONL lines, or CSV data rows (header excluded); `field_count` and `field_list_mismatch_count` appear only on `site_evidence_wide.csv`, as before this change. A file with zero records is still written (an empty JSONL file, or an empty CSV as before) and still listed.
- `included_task_ids`, `included_review_decision_ids`, and `included_acceptance_ids` are sorted (byte order) and de-duplicated in the manifest, whatever order the batch row stores. `evidence_version_hashes` is the sorted, de-duplicated set of `object_hash` values in `evidence_versions.jsonl`; `review_snapshot_hashes` is the sorted set of `snapshot_hash` values in `review_snapshots.jsonl`.
- `frozen_at` and `manifest_hash` are present only on a frozen bundle. A draft preview, or the live preview of a batch frozen before this change, carries neither and is not a verifiable bundle.
- `supersedes_export_batch_id` is present only when the batch was created to replace an earlier frozen batch.

The bundle carries sixteen files. Twelve existed before this change (`tasks.jsonl`, `task_events.jsonl`, `evidence_drafts.jsonl`, `historical_claims.jsonl`, `review_decisions.jsonl`, `site_occupancies.jsonl`, `derived_target_year_states.jsonl`, `derived_year_locations.jsonl`, `derived_target_year_functions.jsonl`, `derived_state_events.jsonl`, `site_evidence_wide.csv`, and `export_manifest.json` itself). Four are new: `evidence_versions.jsonl` (every `evidence_versions` row of each included task, each an `evidence-version.v1` envelope), `evidence_head_changes.jsonl` (every `evidence_head_changes` row of each included task), `task_acceptances.jsonl` (every `task_acceptances` row of each included task, all outcomes, not only the accepted ones the manifest's `included_acceptance_ids` names), and `review_snapshots.jsonl` (the `review_snapshots` rows named by `review_snapshot_hash` on the included decisions, de-duplicated, sorted by `snapshot_hash`). Row content follows the Convex documents as stored, including `_id` and `_creationTime`, one JSON object per line.

`convex/exports.ts`'s builder is deterministic for a fixed database state: every read is an indexed lookup over a sorted task/decision id list, and nothing but `frozen_at` (passed in, not read fresh) touches the clock.

## Freezing

`exports:freezeExportBatch({ exportBatchId })` (role `curator` or `admin`) is now an **action** orchestrating three internal mutations, so each step is transactional and the action itself holds no state beyond the storage ids it created:

Since PR L1 the three internal mutations and the outcome probe accept a call without an identity when it names the acting curator's user id, who must still be an active curator or admin: the scheduled freeze chain (below) has no identity of its own and acts for the curator recorded on its run. A call with an identity is checked against that identity, as before.

1. **`internal.exports.prepareFreeze({ exportBatchId, userId, attemptId })`.** Requires the batch `draft`. Re-runs, for every included task, the shared authority check `assertTaskExportAuthority(ctx, taskId)` (also called by `createExportBatch`): the task exists and is `pi_accepted`, is not training-excluded, the decision named by the task's latest accepted acceptance (or the newest accepted decision, absent an acceptance row) is still `accepted_for_export`, its pinned `evidence_version_hash` still matches the draft's current hash, and, when it is snapshot-linked, `reviews:assertDecisionSnapshotConsistent` passes. The batch's stored `included_review_decision_ids` and `included_acceptance_ids` must still equal what that recheck returns now, as sorted sets; a difference refuses ("membership changed since it was created ... create a new batch"). For a batch an export run composed, each task's authoritative decision, pinned evidence version, and snapshot hash must also still equal what the run captured (`export_run_members`); a difference refuses ("export authority changed since run ... captured it; compose a new run"). On success it builds the complete bundle at `frozen_at = Date.now()`, computes every file hash and the manifest hash, and records `pending_freeze: { attempt_id, started_at, started_by, manifest, stored_objects }` on the batch, carrying forward the stored-object trail of any earlier attempt it replaces. That is its only write, so any refusal above it leaves the batch completely untouched. The byte budget is applied when a batch is composed or created, not at capture (PR L1 replaced the interim capture-time refusal).
2. **The action stores every file.** For each of the sixteen files it gzip-compresses the plain UTF-8 bytes under the pinned codec ([Stored encoding](#stored-encoding-pr-l1)), stores the gzip bytes with `ctx.storage.store`, records the object on the batch's trail through `internal.exports.recordStoredObject` (which refuses, and the attempt stops, once the attempt is no longer current), reads it back with `ctx.storage.get`, and verifies all four values: the stored SHA-256 and byte length, then, after decoding, the plain SHA-256 and byte length computed before the store call. Any failure, for any file including the manifest itself: delete every blob stored during this attempt (including the one that just failed its own check) and call step 4.
3. **`internal.exports.completeFreeze({ exportBatchId, attemptId, userId, storedFiles })`.** Idempotent for a committed attempt: a batch already frozen with `frozen_by_attempt_id === attemptId` returns the same result again. Otherwise requires the batch still `draft` and `pending_freeze.attempt_id === attemptId` (a second, overlapping attempt replaced it: refuse with "this freeze attempt is no longer current"). Rebuilds the bundle from the current rows with the same `frozen_at` and compares every file's SHA-256 to `pending_freeze.manifest`; any difference means a row changed between capture and completion, and it refuses, naming the file. When the batch carries `supersedes_export_batch_id`, the predecessor is rechecked in the same transaction before any write: it must still be `frozen` with `frozen_files`, not yet superseded, the same country, and covered by this batch's membership (section 5); otherwise completion refuses ("can no longer be superseded; create a new batch without supersedesExportBatchId"). On success it patches the batch (`status: "frozen"`, `frozen_at`, `freeze_completed_at`, `frozen_by_attempt_id`, `bundle_contract`, `manifest_hash`, `frozen_files: [{ filename, storage_id, sha256, byte_length, content_type, encoding, stored_sha256, stored_byte_length, codec }]`), clears `pending_freeze`, deletes the blobs of any trail entry the committed files do not name (objects of attempts that died or were replaced), moves every included task to `exported` with the `exported` event exactly as before this change and stamps `last_export_batch_id` and `last_exported_at` on the task beside that patch (the `exported` transition stays at freeze completion, ruling 12), and marks the earlier batch `superseded` with `superseded_by_export_batch_id` and `superseded_at` (its own bytes and `frozen_files` untouched).
4. **`internal.exports.recordFreezeFailure({ exportBatchId, attemptId, reason })`.** If the batch is still `draft` and either carries no `pending_freeze` or one matching this attempt, deletes the blobs of any trail entry still present (the attempt's own were deleted by the action; carried-forward entries belong to dead attempts), clears `pending_freeze`, and sets `last_freeze_failure: { attempt_id, at, reason }`; an older attempt's belated failure does not clobber a newer, still-current attempt's `pending_freeze`. The action deletes any blobs it stored before calling this and rethrows, so the caller sees the original reason. A failed freeze leaves the batch `draft` and every task where it was. A failed `completeFreeze` call is the one ambiguous case: the transaction may have been rejected, or it may have committed and only its response been lost. Before deleting anything the action asks `internal.exports.freezeAttemptOutcome({ exportBatchId, attemptId })`; a batch that answers with this attempt's committed result is returned as a success and its blobs kept, only a "not committed" answer leads to deletion and step 4, and if the probe itself fails the action keeps every blob and throws naming their storage ids ("outcome could not be established ... blobs were kept") for the operator to reconcile.

The action's return is `{ export_batch_id, status: "frozen", manifest_hash, frozen_at, file_count }`.

## Retrieval

`exports:getExportBundle({ exportBatchId })` (role `curator` or `admin`) is now an **action** returning `{ export_manifest, files, disposition }`. `files` carries the same keyed object of texts as before this change, plus the four new keys (`evidence_versions_jsonl`, `evidence_head_changes_jsonl`, `task_acceptances_jsonl`, `review_snapshots_jsonl`). The typed row arrays the query used to return (`tasks`, `task_events`, ...) are gone: nothing outside `convex/` read them, and they doubled the payload.

- **A batch with `frozen_files`** (frozen, withdrawn, or superseded): every blob is read from storage and verified against `frozen_files`, and the manifest file is parsed and its `manifest_hash` reproduced. An entry with `encoding: "gzip"` is verified on all four values: stored SHA-256 and byte length first, then, after decoding, plain SHA-256 and byte length; an entry without `encoding` (frozen before PR L1) holds plain bytes and is verified on SHA-256 and byte length as before; a mismatch refuses, naming the file and both hashes, and the bundle is never rebuilt from rows. `disposition` carries `stored_bytes: true`, `verified: true`, and `processing_allowed` true only when `status === "frozen"` (a withdrawn or superseded batch still serves its bytes but is not processed further).
- **A `draft` batch, or an `archived` one** (a draft a later composition replaced): built as a live preview through `internal.exports.buildDraftBundle`, with no `frozen_at` and no `manifest_hash`. `disposition` carries the batch's status, `stored_bytes: false`, `verified: false`, `processing_allowed: false`.
- **A legacy frozen batch** (any status with no `frozen_files`, i.e. frozen before this change): served the same live rebuild as a draft, but carrying the row's own `frozen_at`; `disposition` adds `legacy_unfrozen_bytes: true`. Such a batch cannot be re-frozen; a curator creates a new batch.

## Withdrawal and supersession

- **`exports:withdrawExportBatch({ exportBatchId, reason })`** (mutation, `curator` or `admin`): requires a `frozen` batch carrying `frozen_files`; `reason` trims to at least 8 characters (the same floor as PI acceptance notes) and obeys the task reason limit. Sets `status: "withdrawn"`, `withdrawn_at`, `withdrawn_by`, `withdrawal_reason`. Bytes, `frozen_files`, and `manifest_hash` stay. Task statuses are not changed; an exported task returns to review only through `tasks:reopenTask`, as before. Each included task receives a `note_added` event naming the batch and the reason. A draft, already-withdrawn, or superseded batch is refused.
- **`createExportBatch` gains an optional `supersedesExportBatchId`.** The named batch must exist, be `frozen` (not draft, withdrawn, or already superseded), carry `frozen_files`, and be the same country as the new batch. The replacement-membership rule: the new batch must include every task the earlier batch exported, and may add more; an empty batch, or one that drops a predecessor task, is refused at creation ("must include every task it exported; missing ..."), because the dropped task would lose its only processable frozen record. A curator who is not re-exporting those tasks withdraws the earlier batch instead. Until a superseding batch may carry an unchanged `exported` task forward (lean-storage brief, ruling 11), this means every predecessor task must have been reopened, re-reviewed, and re-accepted. The id is stored on the new batch as `supersedes_export_batch_id` and appears in its manifest. The earlier batch's status changes only when the new batch's freeze completes (`completeFreeze`, above, which rechecks all of this against the predecessor's state at that moment). Creating the new batch alone does nothing to the earlier one.
- **`exportBatchStatus` gains the literals `withdrawn` and `superseded`.** No code path writes `exported`, `validated`, or `failed`; since PR L1 a composition that replaces an earlier run writes `archived` on that run's unfrozen drafts.

## Budgeted batches and export runs (PR L1)

A batch must fit one `prepareFreeze` and one `completeFreeze` transaction, which Convex bounds at 16 MiB read, 32,000 documents scanned, 4,096 index ranges read, and a 16 MiB function result. Two budgets, exported from `convex/exports.ts` as starting values (ruling 2), hold a batch inside those caps: `EXPORT_BATCH_BYTE_BUDGET` (6 MiB of plain bundle bytes, the text `prepareFreeze` returns in one result, 37.5% of the result cap) and `EXPORT_BATCH_READ_BUDGET` (10 MiB read, 16,000 documents, 2,048 index ranges: the reads the freeze recheck and bundle build make). `EXPORT_BATCH_MAX_TASKS` (500) guards the batch document itself. A task is measured by running the same reads `prepareFreeze` will run for it, `assertTaskExportAuthority` and `collectBundleRows`, through a read meter (`convex/lib/readMeter.ts`) that counts each terminal query as one index range, each returned document once, and its JSON bytes, and by sizing its share of the bundle exactly as `buildBundle` writes it (its JSONL rows, its CSV rows without the header, which a batch carries once, and its ids in the manifest). A task whose rows alone exceed either budget, or whose recheck refuses, is refused by name.

- **`createExportBatch`** measures each task as it takes it and refuses the batch as soon as the running estimate breaks a budget, naming the task and the budget; an explicit `taskIds` list over budget is refused, never truncated, and automatic selection (no `taskIds`) over budget is refused in favour of the composer. This replaces PR #112's interim gates (the 100-task automatic-selection cap and the refusal at capture). The batch records `estimated_bytes`, `estimated_documents`, and `estimated_index_ranges`.
- **`composeExportBatches({ countryCode })`** (mutation, `curator` or `admin`) starts an export run (`export_runs`) and schedules its composition. Each `internal.exports.composeRunStep` reads the country's `pi_accepted` tasks through `tasks.by_country_status` in creation order from the run's cursor, measures each, and records it in `export_run_members` (task, accepted decision and acceptance ids, the authoritative decision and its pinned evidence version and snapshot hash, the estimate) or as a named refusal, until the step's own reads reach `COMPOSE_STEP_READ_BUDGET` (3 MiB, 6,000 documents, 1,024 ranges), then schedules the next step. Training-excluded tasks are skipped, as `createExportBatch` skips them. Once every task is measured, cutting steps walk the members in order and close a draft batch whenever the next member would break a budget; each composed batch carries `export_run_id`. The run's membership is captured at composition, so the chain freezes exactly that set and a task accepted afterwards waits for the next run (ruling 2). One run per country is active at a time: a run still composing or freezing under a live lease refuses a second composition, and a composition that follows a composed, stopped, or lapsed run marks it `replaced` and archives its unfrozen drafts (`archived_at`, `archived_by`, `archived_reason`), deleting any dead attempt's trail with them; frozen batches keep their bytes.
- **`freezeCountryBatches({ countryCode })`** (action, `curator` or `admin`) starts or resumes the freeze chain of the country's latest composed run as the calling curator, freezes the run's first draft batch itself (so a refusal reaches the caller), and each settled freeze schedules the next invocation, `internal.exports.freezeRunStep`, in the same transaction that releases the lease. One invocation freezes one batch under the run's lease (`EXPORT_RUN_LEASE_MS`, 15 minutes, longer than an action may run, renewed between the phases of a freeze). Each invocation rechecks that the run's curator is still an active curator or admin and stops the run if not. A batch whose freeze fails stays `draft` with its `last_freeze_failure`, and the run stops with `last_error` naming it; it is never skipped. A curator re-run resumes from that batch; if its membership has drifted, a new composition replaces the run. When no draft batch of the run remains, the run is `completed`.
- **`getExportRun({ countryCode } | { runId })`** (query, `curator` or `admin`) returns the run: status and phase, member, refusal, batch, and frozen-batch counts, the first 20 refusals, the lease, and the last error.

Measured on an isolated local backend (Convex local backend, 2026-09-24): 201 synthetic `pi_accepted` NZ tasks seeded through the real submission, snapshot, review, and PI acceptance path, each with an 11 KB generated wide row and a 25 KB task brief, about 136 KB of plain bundle per task (the brief's realistic cycle-1 task is 141 KB). The figures are the backend's own usage statistics per function execution; it does not report index ranges, so the meter's count is given for those.

| Step | Bytes read | Documents | Result | Runtime |
| --- | ---: | ---: | ---: | ---: |
| `composeRunStep`, estimating (15 steps) | 3.0 to 4.0 MiB | 196 to 246 | none | 0.04 to 0.07 s |
| `composeRunStep`, cutting (1 step, 201 members) | 0.3 MiB | 405 | none | 0.02 s |

The run cut the 201 tasks into five batches (42, 42, 42, 42, and 33 tasks); for each, the estimated bundle bytes exceeded the built bundle by 6.7 KB (the manifest allowance), and the meter's read estimate for a 42-task batch (9.6 to 9.7 MiB, 630 documents, 840 index ranges) matched or slightly exceeded the backend's measured reads. The byte and read budgets bind at almost the same point for tasks of this shape; the read budget binds first when task rows are read twice (the task row and the snapshot are read by both the recheck and the build). ## Stored encoding (PR L1)

Every stored file is gzip-compressed (ruling 3) with the pure-JS codec `fflate`, pinned exactly in `package.json` (0.8.3), at level 6, with a deterministic header: modification time 0, no filename, no comment, and fflate's fixed operating-system byte (3). One plain file under one codec record therefore gives one stored byte sequence. The codec record, `{ name: "fflate", version, level, header: { mtime: 0, filename: false } }`, is stored on every `frozen_files` entry beside `encoding: "gzip"`, `stored_sha256`, and `stored_byte_length`, so the stored bytes can be reproduced from the plain bytes, not only checked; `sha256` and `byte_length` keep describing the plain bytes, as the manifest's `files[]` does. The codec id `fflate-<version>-l<level>` names one stored representation, and the object key of ruling 3, `objects/sha256/<plain sha256>/<codec id>.gz`, is recorded on each trail entry now and becomes the key in the durable bucket of PR L2; a codec upgrade writes a new key beside the old one. `convex/lib/bundleCodec.ts` holds the codec; its tests check the pin against the installed package, the exact header bytes, byte-identical output under a different clock, decoding by the platform's own gzip reader, and each of the four verification failures. fflate does not check the gzip trailer's CRC, which is why the plain SHA-256 check is mandatory on every read. On the synthetic run above, 27.4 MB of plain bundle stored as 1.4 MiB (18 times smaller); that data is repetitive, and the brief's measured 7.4 times per file on a realistic bundle remains the planning figure.

`pending_freeze.stored_objects` is the trail: each entry records the attempt, file, object key, storage id, the four values, the codec id, and when it was recorded, as soon as the object is stored and before it is read back, so an attempt that dies mid-freeze leaves its objects listed on the batch. A later attempt carries the trail forward; its completion deletes the blobs no committed file names, its failure deletes all of them, and a composition that archives the draft deletes them with it. Deletion inside a mutation checks the `_storage` system table first, so a blob another path already removed is skipped.

## Schema additions

`export_batches`, all optional and additive; existing rows are untouched: `pending_freeze: { attempt_id, started_at, started_by, manifest: v.any(), stored_objects }`, `last_freeze_failure: { attempt_id, at, reason }`, `freeze_completed_at`, `frozen_by_attempt_id`, `bundle_contract`, `manifest_hash`, `frozen_files: [{ filename, storage_id: v.id("_storage"), sha256, byte_length, content_type, encoding, stored_sha256, stored_byte_length, codec }]`, `withdrawn_at`, `withdrawn_by: v.id("users")`, `withdrawal_reason`, `supersedes_export_batch_id`, `superseded_by_export_batch_id`, `superseded_at`, and since PR L1 `export_run_id`, `estimated_bytes`, `estimated_documents`, `estimated_index_ranges`, `archived_at`, `archived_by`, `archived_reason`, with the index `by_export_run_status`. `tasks` gains the optional `last_export_batch_id` and `last_exported_at`. Two new tables: `export_runs` (indexes `by_run_id`, `by_country_started`) and `export_run_members` (indexes `by_run_seq`, `by_run_task`, `by_export_batch`).

## Limits and lean-storage levers

The hashes are small; the copies are not. A frozen batch stores every row of every included task once, a snapshot-linked decision stores a full copy of its task's review state, and every evidence version stores a full copy of the evidence content. In the committed fixture (`schemas/fixtures/pow-export-bundle.v1`, one task, one guided draft, one snapshot-linked acceptance) the bundle is 45 KB, the snapshot 16 KB, and the three versions 7.2 KB together; live drafts carry the generated wide row and run larger. PR L1 bounds each batch by the budgets above, freezes a country in as many batches as it needs, and stores compressed bytes; every superseding batch still keeps the earlier batch's bytes, so storage grows with the number of freezes, not only with the number of places. The remaining levers are the lean-storage brief's later steps: the durable, locked R2 home (PR L2), then slimmer evidence versions and snapshots (PRs L3 and L4).

## Out of scope

The export queue, PI batch release, the decision hash version 2 envelope, proposal pinning, reading the accepted version's stored envelope in place of the draft row for `site_evidence_wide.csv`, a portal surface for batches, and any migration of existing frozen batches. `pow export verify` and the materialisation script's handling of the new bundle shape are documented in `docs/api/workflow-scripts.md` and the `pow` command-line help.
