# Server-side retry safety for client submissions

**Status: design brief for JB's ruling, 2026-10-02.** JB selected the server-side direction ("then option 2") on 2026-10-02. The contracts, migration policy and recommendations below await approval. This brief adopts no implementation or deployment. Its primary module is **Evidence Intake**, with dependencies on Shared Task List and source registration; reviewer acceptance and master release retain their existing authority.

## The server must distinguish a retry from an edited submission

A lost response leaves the member uncertain whether a submission committed. Today, an existing submission key can return the earlier result even when the request contains changed evidence. Conversely, the client-side repairs in [PR #153, rounds 19–24](https://github.com/go-bayes/places-of-worship/pull/153#issuecomment-5939867753) sometimes gave unchanged evidence a new identifier and created duplicates. Browser state, prerequisite writes and submitted content proved different objects to compare.

The proposed server rule is: the same member and submission identifier with the same canonical request digest returns the original receipt; a different digest produces a typed refusal before any evidence write. The client responds to that refusal by minting a new identifier and resending the attempted content once. Transport failures retain the identifier. A new identifier authorises a new attempt through the existing intake and correction gates; reviewed tasks retain their intake restrictions.

## Current coverage and gaps

The inspected baseline is public `main` at `f8afd687878f182489e35f564af0e1acb5f9e2ec`. Five exported mutations accept `clientSubmissionId`. The portal has six corresponding send paths because rapid-entry periods and the occupancy pane share a mutation; general draft submission is also an API surface.

| --- | --- | --- |

Existing retry results are partly reconstructed from mutable rows. Rapid and historical responses can report later statuses; occupancy and guided retries return empty derivation arrays. The proposed receipt instead stores the original result, including arrays and version identifiers. `deduped` is the only response member changed on replay, from `false` to `true`; status fields describe the original commit. Current status comes from the ordinary query API.

The portal also calls `sources:createSource`, `tasks:createIssueTask`, and `evidence:saveEvidenceDraft` before final submission. Those calls identify their inputs through source, task or draft fields. `createIssueTask` reuses an open issue, which can change after submission; `createSource` matches an active title and country, a weaker criterion than request equality. `tasks:createManualCandidateTask` is an adjacent independent write requiring its own receipt if used as a prerequisite. Quick photo uploads attachments after recording the observation. Quick photo uses the rapid mutation. Tokenless `submitUnresolvedNote`, uploads and other independent writes require explicit scope decisions before claiming that every portal write is retry-safe.

## Receipt and transaction contract

Add a `client_submission_receipts` table indexed by authenticated project `member_id` and `client_submission_id`. Each immutable row contains `operation`, `request_contract`, `request_digest`, `result`, `resolved_bindings`, optional `replaces_submission_id`, and server `recorded_at`. `result` has a closed, operation-specific validator. `resolved_bindings` records the source snapshot, task, parent version and derived defaults used by the committed attempt. Retain existing `evidence_submission_receipts` and evidence-version hashes: their content and lineage contracts serve a different purpose.

The proposed key is global within a project member, with the operation included in the digest. Reusing a token across operations therefore produces a conflict. Existing route-prefixed version receipts continue to be written. Internal steps use the outer receipt or a separate `(member, outer id, step)` namespace; child and outer writes have distinct receipt keys. An indexed lookup followed by insertion in the same transaction establishes uniqueness under concurrent requests; implementation must verify that behaviour against a real local Convex backend, because uniqueness depends on transactional conflict handling.

Each handler follows six ordered steps:

1. Authenticate the active member, resolve linked credentials to the same project user, verify role and receipt-access authority, and enforce bounded input decoding and request-attempt limits.
2. Find the receipt and normalise the request under its stored contract version, or under the current version for a new key. Use recorded bindings for a retry; avoid refreshing mutable prerequisite results.
3. Compare the digest. An equal digest returns the saved result before task-status gates, prerequisite writes, rate charges for new evidence, or events. A mismatch throws `ConvexError({ code: "CLIENT_SUBMISSION_CONTENT_CONFLICT", operation, clientSubmissionId, canResubmitWithNewId: true })`. The error contains only the stated fields from the caller's attempt.
4. For a new key, apply the existing ownership, country, source, privacy, task-status and scientific validation rules. A replacement attempt also validates its predecessor receipt and permitted correction target.
5. Charge the applicable creation quotas and perform prerequisite writes, evidence writes, derived-state updates, versions and events in the same transaction.
6. Insert the digest, resolved bindings and complete result in that transaction. A failed transaction rolls back the receipt and all evidence writes. A committed transaction with a lost reply is recoverable by its receipt.

`request_digest` is the `sha256:` hash of the UTF-8 canonical JSON of `{ contract: "submission-request.v1", operation, content }`, using the existing [`canonicalJsonStrict` and SHA-256 implementation](../../convex/lib/canonicalJson.ts). The server computes the authoritative digest from the request. Authentication scopes the lookup and is excluded from content, as are the submission identifier and retry bookkeeping. Keep each receipt's normaliser available while its tokens remain retryable; a future normalisation change gets a new contract version.

## Canonical content is an explicit input projection

The request normaliser and writer must consume the same validated content object. Hashing a separate approximation of the saved data would repeat the browser failure on the server. The following rules define the proposed projection; implementation must reconcile each writer with these rules.

For declared text inputs, trim leading and trailing whitespace; retain internal whitespace, case and Unicode sequences. Empty optional text becomes absent; required empty text fails validation. Uppercase country codes and apply the existing candidate default `VU` when country is omitted; existing-task requests derive country from the task binding. Reject a supplied country inconsistent with that binding. Retain numeric coordinates at their submitted precision. Apply declared boolean defaults, including `flagForDiscussion: false`. Omit undefined optional members; retain meaningful `false`, zero and allowed null values. Reject unknown fields outside validated extension objects.

Object-key order follows `pow-canonical-json.v1`. Sort occupancy segments by unique `segment_index`, reject duplicate indices, and retain the index as content. Sort probable-place links by `task_id`, reject duplicates, and retain only the selected task identifiers: `name` and `distance_m` are display context. Keep function-chain changes in their submitted order. Sort and deduplicate task `targetYears` as a set. All other arrays retain order. Apply date-mode validation before projection and refuse incompatible date fields.

The five mutation projections are specified below. Proposed atomic entry points use the same projections plus their prerequisite descriptors from the next section.

## Prerequisites must have stable results

Prefer new atomic submission entry points that accept declarative prerequisites and call shared server helpers. For rapid entry, combine optional source registration, optional revision-task creation, observation and optional initial periods/chain. For guided entry, combine the intended draft content, optional revision creation and final submission with periods. The server resolves prerequisites after the receipt comparison for a new key and saves their results with the receipt. The client resends the same prerequisite descriptors.

The prerequisite descriptors have three defined content projections:

1. **Source registration:** `countryCode`, `sourceType`, `title`, `provider`, `url`, `archiveRef`, `licence`, `publicationDate`, `consultedDate`, `accessLimits`, `notes`, plus a discriminant distinguishing registration, an existing `source_id`, and an unregistered citation. A title/country match is merely a candidate match. Reuse requires compatible source content; conflicting register entries produce a source conflict requiring member action. Registration failure fails the atomic attempt. A member may explicitly choose the unregistered citation path on a later attempt. Retain the original descriptor through reload and source selection; selecting the source returned by the same receipt can resolve to that recorded descriptor only after server verification of the binding.
2. **Task creation:** for revision issues, all `createIssueTask` arguments except `clientContext`: `countryCode`, `name`, `issueType`, `note`, `latitude`, `longitude`, `siteId`, `osmId`, `relatedSiteId`, `sourceTitle`, `sourceUrl`, `targetYears`, `locationAssertion`, `originalLatitude`, `originalLongitude`, `assignToReporter`, `sourceTaskId`. For manual tasks, all `createManualCandidateTask` arguments except `clientContext`: `countryCode`, `name`, `address`, `locality`, `latitude`, `longitude`, `priority`, `taskType`, `targetYears`, `taskBrief`, `sourceNote`, `locationAssertion`, `probableSameAs`. Omitted defaults resolve once and are retained in bindings. Receipt replay returns the original task even after its status changes.
3. **Parent evidence:** either the full intended draft projection in the atomic request or an immutable saved-content reference whose digest the server computed. A saved-content reference must name immutable bytes and task/owner bindings. If implementation retains mutable draft saves, final submission requires a compare-and-set against the saved content and returns `PARENT_CONTENT_CHANGED` on mismatch. That error requires reload/reconciliation under the retained submission identifier. Final submission must verify the intended saved content even when the client has a cached save receipt.

The A/B/A failure is a required acceptance case: save A, lose a later response, save B, restore A, submit A with A's periods. The server must submit A atomically, or refuse a stale mutable-draft reference. Returning A's cached save receipt and then submitting the current B row is forbidden. A genuine retry returns from the receipt lookup before draft-saving, irrespective of regenerated validation timestamps.

Separate historical claims and later occupancy submissions pin their parent receipt/version when the member starts sending. After the first commit, a retry uses that binding even if review has changed the current parent. A new edited attempt must pass the current parent and task gates. If atomic grouping is impractical, every prerequisite needs the same digest-and-receipt protocol, durable step identifiers and immutable output bindings before its dependent write proceeds. Period handover must retain the retry identity until acknowledgement.

A conflict replacement includes `replacesSubmissionId` naming the refused attempt. The server binds a same-operation replacement to the predecessor's created task/evidence family and records correction lineage. The existing nomination remains the correction target. Existing correction gates apply. A changed target outside the authorised correction scope returns a reconciliation error. The replacement reference enters canonical content, is verified against the same member, and is immutable across retries. JB's ruling on correction scope below is required before implementation.

## The client retains identity and sends explicit content

Mint a cryptographically random submission identifier when the member first presses Send. Retain that identifier for the unresolved logical send across automatic retries, manual retries, edits and restoration. On `CLIENT_SUBMISSION_CONTENT_CONFLICT` alone, mint a replacement identifier, attach the predecessor reference, and resend the same attempted content once. A second conflict stops the loop. Cross-operation token reuse produces a conflict permitting a fresh attempt. The predecessor grants correction bindings only within the same operation. A lost response to the replacement retries the replacement identifier. An independently started submission after acknowledged completion gets its own first-send identifier.

Automatic retries resend an immutable request snapshot. Manual retries may submit the member's edited content under the retained identifier; the server decides whether the content changed. Listeners, autosave, rendering, restore and file reselection retain the identifier and defer equality decisions to the server. Persist the request's semantic state, source intention, captured dates, prerequisite descriptors, identifier and replacement relationship as a member-owned record before transport when storage is available. Restore that record before enabling Send. The form and request builder must use the same semantic state. The server compares the content it receives, including any blank or stale values introduced by the browser.

When device storage is blocked, retain the pending identifier and snapshot in memory. A reload that destroys the only local identifier breaks the association between the form and the attempted submission. Require receipt/history reconciliation before offering a fresh send for an uncertain outcome. Explain uncertainty as "The response was lost; check whether the submission was recorded." Reserve a definitive failure message for a definitive refusal. File upload recovery uses the recorded task and its own upload identity; file reselection resumes the upload step. An attachment receipt contract is separate implementation work.

The transport must retain structured Convex error data. Parse the error code and operation; string matching on an error message or an HTTP status is insufficient. Network failure, authentication expiry, validation refusal, rate limiting, legacy uncertainty and parent-content conflict retain the identifier. Rate limiting respects server retry timing.

## C1 keeps simple sign-out

PR #153 at `6a054f5bcefc21a72010b8d7c688955d9f1f3970` removes the attempted client fingerprint machinery and retains simple sign-out. This design assigns content comparison to the server protocol. Cancelling sign-out retains the current work. Confirmed sign-out clears member-owned forms, files, retry records and timers, and prevents a stale callback from writing storage, repainting a signed-out view, or sending a replacement under a later member's session.

An in-flight mutation can commit despite local sign-out. Its server receipt remains attached to the original project user. Subsequent sign-in uses history reconciliation if the local token was cleared. Server commit and local sign-out have separate lifecycles. Session expiry may retain a record only under C1's ownership guards and may resume only after authentication as the same project member. Linked Google/Clerk credentials must resolve to that same member. Reject requests by a different member to replay, inspect or adopt the pending request.

## Additive storage, explicit legacy uncertainty

Introduce the new receipt table, optional references and new versioned atomic functions additively. Keep existing function validators, return shapes, evidence-version envelopes and historical rows readable. Tokenless general submissions retain their existing content-based behaviour and fall outside the new keyed-retry guarantee. Old endpoints can write new request receipts where their inputs are sufficient, but their mutable-draft/prerequisite ambiguity remains until clients use the new contract. Narrowing old validators or making optional tokens mandatory is a separate compatibility change.

On a miss in the new table, probe the existing rapid, historical and occupancy submission-key indexes and route-prefixed version receipts before treating the token as new. Add an index on `evidence_drafts.guided_submission_key` to find legacy guided submissions, including zero-period submissions predating version receipts. Rows predating request digests leave request equality unverified. Multiple legacy operations sharing a token require reconciliation under the proposed global member/token namespace. For a legacy-key hit, return typed `CLIENT_SUBMISSION_LEGACY_UNVERIFIED`, with an authorised locator for reconciliation and `canResubmitWithNewId: false`. The new client must show the earlier record before a member chooses a correction. Blindly accepting the incoming request as the old digest could lose an edit; automatically rotating could duplicate an earlier successful send. Legacy refusals may use the older client error channel until rollout.

Backfill a digest only when immutable records establish every original request field and resolved binding under a documented normaliser. Existing evidence `content_hash` alone omits request inputs such as submission notes and candidate details. Leave ambiguous rows explicitly legacy; retain `pre_contract` version unavailability where applicable. Any backfill is a separately authorised data mutation with a manifest and counts. Keep receipt keys, or durable tombstones requiring reconciliation, for as long as the associated submission exists. Retired tokens remain reserved.

Deploy additive backend support before switching clients, with capability detection and a clear upgrade boundary. Changed legacy error behaviour requires its own compatibility assessment. Stage and review that behaviour explicitly. [Evidence-version documentation](evidence-versions.md) and the [API inventory](../api/convex-functions.md) describe today's behaviour; update them with the implementation, alongside the RA guide for changed retry messages. A FAQ entry should follow adoption, when collaborators have a settled contract to follow.

## Abuse limits apply to attempts and new writes

Retain the current creation quotas in [`convex/lib/rateLimits.ts`](../../convex/lib/rateLimits.ts): rapid entry 120 per member/hour and 500 globally/hour; historical claims and occupancy sets each 240 per member/hour and 1,000 globally/hour. Charge a successful receipt once, including every created component of an atomic request. Add explicit quotas for guided/general submissions and prerequisite creation, including submissions with an empty period array.

Use a separate bounded attempt allowance for successful replays, conflicts and malformed requests. A recommended starting allowance is 60 authenticated requests/minute/member with a burst of 20, plus a deployment-wide ceiling set from measured capacity. Enforce failed-attempt accounting outside any transaction that throws and rolls back; verify the chosen limiter mechanism before release. Continue payload, segment-count, string-length, source, role and country bounds before expensive work. Charge conflict responses and successful replays against the attempt allowance only. Charge fresh submissions against member/global creation quotas. Keep receipts private and avoid logging canonical evidence, raw authentication tokens or content digests to public telemetry.

## Six rulings requested from JB

1. **Receipt identity and scope.** Recommend a global `(project member, submission id)` request receipt with operation in the digest, covering all five token-bearing mutations and atomic prerequisites. Keep evidence-version receipts separately. Require a separate scope decision for standalone unresolved notes and attachment uploads.
2. **Atomic prerequisites.** Recommend atomic source/task/observation submission and atomic guided save-and-submit. Treat source-registration failure as an explicit refusal; offer unregistered citation only as a member choice. Require immutable parent references for remaining multi-step flows.
3. **Edited retries and corrections.** Recommend one automatic replacement after a content-conflict refusal, with a verified predecessor reference. Keep corrections in the original task/evidence family where existing rules permit; require reconciliation when target changes or review gates prevent correction.
4. **Legacy rows.** Recommend typed uncertainty and reconciliation for missing digests. Backfill only provable requests under separate authority; retain keys/tombstones for the life of the submission. Use an explicit temporary legacy-client refusal during the reviewed rollout.
5. **Sign-out and local loss.** Recommend C1's deliberate clearing and member ownership rules. Treat forgotten identifiers after sign-out or blocked-storage reload as reconciliation cases. Receipt history recovery is required before advertising recovery across those boundaries.
6. **Limits and delivery order.** Recommend retaining current creation quotas, adding the proposed attempt allowance and explicit prerequisite/guided quotas, and measuring a global attempt ceiling before enabling new clients. Implement only after rulings, then obtain routine and reserved-model review of the final design/implementation heads under the repository rules. Deployment, migration and closure require their own authority.
