# Server-side retry safety for client submissions

**Status: design brief for JB's ruling, 2026-10-02.** JB selected the server-side direction ("then option 2") on 2026-10-02. The contracts, legacy policy and recommendations below await approval. Implementation and deployment follow JB's rulings under separate authority. The brief's primary module is **Evidence Intake**, with dependencies on Shared Task List and source registration; reviewer acceptance and master release retain their existing authority.

## The server must distinguish a retry from an edited submission

A lost response leaves the member uncertain whether a submission committed. Today, an existing submission key can return the earlier result even when the request contains changed evidence. Conversely, the client-side repairs in [PR #153, rounds 19–24](https://github.com/go-bayes/places-of-worship/pull/153#issuecomment-5939867753) sometimes gave unchanged evidence a new identifier and created duplicates. The browser compared form state while the server compared the request it received, and the two differed in every round.

The proposed server rule is: the same member and submission identifier with the same canonical request digest returns the original receipt; a different digest produces a typed refusal before any evidence write. The conflict outcome includes the original committed result so the client can identify the correction target. A fresh identifier permits an attempt through the existing intake and correction gates. Candidate-field corrections require the scope ruling below. Transport failures retain the identifier.

## Current coverage and gaps

The portal has six corresponding send paths because rapid-entry periods and the occupancy pane share a mutation; general draft submission is also an API surface.

Existing retry results are partly reconstructed from mutable rows. Rapid and historical responses can report later statuses; occupancy and guided retries return empty derivation arrays. The proposed receipt instead stores the original result, including arrays and version identifiers. `deduped` is the only response member changed on replay, from `false` to `true`; status fields describe the original commit. Current status comes from the ordinary query API.

The portal also makes prerequisite calls: `sources:createSource` finds or creates a source by active normalised title and country; `tasks:createIssueTask` reuses an open issue; `evidence:saveEvidenceDraft` overwrites a draft by its identifier. Source registration ignores differing metadata on a match. `tasks:createManualCandidateTask` independently creates a candidate task. Guided revision uses `evidence:reviseEvidenceDraft`, which resolves the latest submitted draft or unresolved note and creates or reuses an editable revision. Quick photo records an observation through the rapid mutation and then uploads attachments. Tokenless `submitUnresolvedNote` and attachment uploads remain outside the proposed receipt contract.

## Receipt and transaction contract

Add a `client_submission_receipts` table indexed by authenticated project `member_id` and `client_submission_id`. Each immutable row contains `operation`, `request_contract`, `request_digest`, `result`, `resolved_bindings`, and server `recorded_at`. `result` has a closed, operation-specific validator. `resolved_bindings` records the source snapshot, task, parent version and derived defaults used by the committed attempt. Retain existing `evidence_submission_receipts` and evidence-version hashes: their content and lineage contracts serve a different purpose.

The proposed key is global within a project member, with the operation included in the digest. Reusing a token across operations therefore produces a conflict. Existing operation-prefixed version receipts continue to be written. Prerequisite helpers use the outer receipt only. Convex mutations provide [serializable transactions](https://docs.convex.dev/database/advanced/occ). An indexed lookup followed by insertion in the same transaction therefore safely establishes uniqueness; concurrent requests must also be tested against a real local Convex backend.

Each handler follows six ordered steps:

1. Authenticate the active member, resolve linked credentials to the same project user, verify role and receipt-access authority, and enforce bounded input decoding and request-attempt limits.
2. Find the receipt and normalise the supplied request under its stored contract version, or under the current version for a new identifier. Resolved bindings remain audit data; the digest describes the supplied request.
3. Compare the digest. An equal digest returns `{ outcome: "committed", ...result }` before task-status gates, prerequisite writes, creation charges or events. A mismatch returns `{ outcome: "content_conflict", operation, clientSubmissionId, canResubmitWithNewId: true, committedResult }`, where `committedResult` is the caller's original receipt result. Returning the conflict as a value allows the attempt charge to commit.
4. For a new identifier, apply the existing ownership, country, source, privacy, task-status and scientific validation rules. Apply the correction scope chosen in R-I2.
5. Charge the applicable creation quotas and perform prerequisite writes, evidence writes, derived-state updates, versions and events in the same transaction.
6. Insert the digest, resolved bindings and complete result in that transaction, and return `{ outcome: "committed", ...result }`. A failed transaction rolls back the receipt and evidence writes. A committed transaction with a lost reply is recoverable by its receipt.

The result is a discriminated union; the client branches on `outcome`. R-I2(a) additionally returns `correction_required` for unsupported candidate edits. Validation refusals throw and remain uncharged because [Convex rolls back their transaction](https://docs.convex.dev/functions/mutation-functions#transactions). Conflicts write only attempt accounting. Successful replay also charges only the attempt allowance.

`request_digest` is the `sha256:` hash of the UTF-8 canonical JSON of `{ contract: "submission-request.v1", operation, content }`, using the existing [`canonicalJsonStrict` and SHA-256 implementation](../../convex/lib/canonicalJson.ts). The server computes the authoritative digest from the request. Authentication scopes the lookup and is excluded from content, as are the submission identifier and retry bookkeeping. Keep each receipt's normaliser available while its tokens remain retryable; a future normalisation change gets a new contract version.

## Canonical content is an explicit input projection

The request normaliser and writer must consume the same validated content object. Hashing a separate approximation of the saved data would repeat the browser failure on the server. The following rules define the proposed projection; implementation must reconcile each writer with these rules.

For declared text inputs, trim leading and trailing whitespace; retain internal whitespace, case and Unicode sequences. Omit empty optional text; required empty text fails validation, except that an empty candidate name becomes `"Unknown place of worship"`. Uppercase country codes and apply the existing candidate default `VU` when country is omitted; existing-task requests derive country from the task binding. Reject a supplied country inconsistent with that binding. Retain numeric coordinates at their submitted precision. Apply declared boolean defaults, including `flagForDiscussion: false`. Omit undefined optional members; retain meaningful `false`, zero and allowed null values. Reject unknown fields outside validated extension objects.

Object-key order follows `pow-canonical-json.v1`. Sort occupancy segments by unique `segment_index`, reject duplicate indices, and retain the index as content. Sort probable-place links by `task_id`, reject duplicates, and retain only the selected task identifiers: `name` and `distance_m` are display context. Keep function-chain changes in their submitted order. Sort and deduplicate task `targetYears` as a set. All other arrays retain order. Apply date-mode validation before projection and refuse incompatible date fields.

## Atomic entry points include prerequisite intent

Use new atomic submission entry points that accept declarative prerequisites and call shared server helpers. For rapid entry, one mutation combines optional source registration, optional task creation, observation and optional initial periods/chain. For guided entry, one mutation combines the full intended draft content, optional source/task creation, optional `evidence:reviseEvidenceDraft` creation or reuse, and final submission with periods. The server resolves prerequisites after receipt comparison for a new identifier and records their results as audit bindings. Autosave retains `saveEvidenceDraft`, whose overwrite by draft identifier is idempotent; final submission uses the content in the atomic request.

The prerequisite descriptors have four content projections:

1. **Source registration:** `countryCode`, `sourceType`, `title`, `provider`, `url`, `archiveRef`, `licence`, `publicationDate`, `consultedDate`, `accessLimits`, `notes`, plus a discriminant distinguishing registration, an existing `source_id`, and an unregistered citation. Keep the current title/country find-or-create behaviour, including reuse of stored metadata on a match. Record the resolved `source_id` and source snapshot as bindings. Retain the submitted descriptor through retries, reload and selection of the source returned by the submission.
2. **Task creation:** for revision issues, all `createIssueTask` arguments except `clientContext`: `countryCode`, `name`, `issueType`, `note`, `latitude`, `longitude`, `siteId`, `osmId`, `relatedSiteId`, `sourceTitle`, `sourceUrl`, `targetYears`, `locationAssertion`, `originalLatitude`, `originalLongitude`, `assignToReporter`, `sourceTaskId`. For manual tasks, all `createManualCandidateTask` arguments except `clientContext`: `countryCode`, `name`, `address`, `locality`, `latitude`, `longitude`, `priority`, `taskType`, `targetYears`, `taskBrief`, `sourceNote`, `locationAssertion`, `probableSameAs`. Omitted defaults resolve once and remain in audit bindings. Receipt replay returns the original task even after its status changes.
3. **Draft content:** the full intended guided/general draft projection above, with its task and owner bindings. Atomic submission saves that content and submits the same bytes with the supplied periods and chain.
4. **Guided revision:** `taskId` and normalised `intent` (`correction` or `new_observation`), the inputs of `reviseEvidenceDraft`; omitted intent stays omitted in the digest and retains an existing revision's intent or defaults a new revision to `correction` during resolution. After receipt comparison, the committing transaction pins the source draft, its version and the reused-or-created revision draft as bindings, and throws a validation refusal for an intent mismatch with an editable revision.

The A/B/A acceptance case submits A with A's periods: save A, lose a later response, save B, restore A, submit the full A projection atomically. The atomic writer uses the submitted A content even when the saved row contains B. A genuine retry returns its receipt before draft-saving, irrespective of regenerated validation timestamps. Separate historical claims and later occupancy submissions identify their parent by `parentEvidenceDraftId`; any resolved parent versions remain audit bindings. A fresh submission passes current parent and task gates.

## Candidate correction scope requires a ruling

The current rapid correction path reuses the task unchanged. Candidate name, address, locality, pin geometry, location assertion and reciprocal links are written at candidate creation. An observation correction leaves the original pin and links unchanged.

After a same-operation rapid-entry conflict, use the committed result's `task_id` as `taskId` to attempt an observation correction under a fresh identifier, subject to `CORRECTION_STATUSES` and the existing observer/ownership gates. For candidate-targeted corrections, the optional `candidateComparison` includes the attempted candidate projection in the request and digest. Accept it only when the target task has `candidate_site_id`; refuse it otherwise. Compare it with the stored task name (using the `"Unknown place of worship"` default), trimmed address and locality, geometry, `initial_location_assertion` and probable-same-place references under the candidate normalisation rules. Under recommended R-I2(a), any candidate-field difference returns `{ outcome: "correction_required", taskId, fields }` before evidence writes, and the member is told to nominate a correction separately. The refused request leaves the task and observation unchanged. Under R-I2(b), a new attributed candidate-correction write would record before/after values, actor and time, update geometry and location assertion together, and atomically add or remove reciprocal links on affected tasks. That write requires its own validated content projection and review gates before implementation. Cross-operation conflicts require the member to reconcile the intended form and target.

## The client retains identity and sends explicit content

The browser keeps `{ id, snapshot }` of the last request sent per form; any Send while that record is unacknowledged uses that identifier (automatic retries resend the snapshot; manual Send sends the current request); acknowledgement or a conflict outcome clears the record, and the server decides equality.

Submission identifiers are cryptographically random v4 UUIDs, validated by [`assertRapidSubmissionId`](../../convex/lib/rapidEntry.ts); current candidate and evidence identifiers embed the UUID. Persist the pending record under the authenticated member before transport when storage is available, and restore it before enabling Send. After a same-operation content conflict, the client may make at most one automatic attempt under a fresh identifier: a rapid observation correction on the committed task under R-I2, a fresh occupancy submission, or a fresh guided/general submission with revision intent `correction` when revising. A historical-claim conflict displays the committed claim and makes no automatic attempt: a fresh identifier would add a second claim. A lost reply retains the new identifier and snapshot; a second conflict stops automatic resubmission. Validation refusal, authentication expiry and rate limiting retain the pending identifier, with retries respecting server timing.

Add `getClientSubmissionReceipt({ clientSubmissionId })`, returning the authenticated member's own receipt or `null`. Use the query to recover uncertain outcomes when the identifier remains available after sign-in or a storage failure. Confirmed sign-out and a reload with blocked storage can erase the identifier. If the identifier is lost, the member inspects the task list: a matching submission record establishes that the send committed, but receipt lookup and retry of that attempt are unavailable. Explain uncertainty as "The response was lost; check whether the submission was recorded." File reselection resumes attachment recovery against the recorded task; an attachment receipt contract remains separate work.

## C1 keeps simple sign-out

PR #153 removed the attempted client fingerprint machinery at `6a054f5b` and retains simple sign-out; at `f2c505ca` it also binds every device record to the admitted member and bounds Clerk startup. This design assigns content comparison to the server protocol. Cancelling sign-out retains the current work. Confirmed sign-out clears member-owned forms, files, retry records and timers, and prevents a stale callback from writing storage, repainting a signed-out view, or sending a replacement under a later member's session.

An in-flight mutation can commit despite local sign-out. Its server receipt remains attached to the original project user. After subsequent sign-in, a retained identifier permits `getClientSubmissionReceipt`; a cleared identifier requires the task-list check above and prevents retry of that attempt. Server commit and local sign-out have separate lifecycles. Session expiry may retain a record only under C1's ownership guards and may resume only after authentication as the same project member. Linked Google/Clerk credentials must resolve to that same member. Reject requests by a different member to replay, inspect or adopt the pending request.

## Additive storage, explicit legacy uncertainty

Introduce the new receipt table, optional references and new versioned atomic functions additively. Keep existing function validators, return shapes, evidence-version envelopes and historical rows readable. Tokenless general submissions retain their existing content-based behaviour and fall outside the new keyed-retry guarantee. Old endpoints can write new request receipts where their inputs are sufficient, but their mutable-draft/prerequisite ambiguity remains until clients use the new contract. Narrowing old validators or making optional tokens mandatory is a separate compatibility change.

On a miss in the receipts table, the operation's existing submission-key lookup identifies a legacy hit; the guided variant compares `guided_submission_key` on the supplied `evidenceDraftId`, as [`evidence:submitEvidenceDraftWithOccupancies`](../../convex/evidence.ts) does today. On a legacy hit, return today's deduped result in the new `{ outcome: "committed", ...result, legacy_unverified: true }` shape. The marker states that request equality is unverified. Retain receipt identifiers for the life of the associated submission.

Deploy additive backend support before switching clients. Versioned endpoints expose the new result union while existing clients keep their current return shapes. [Evidence-version documentation](evidence-versions.md) and the [API inventory](../api/convex-functions.md) describe today's behaviour; update them with implementation, alongside the RA guide for changed retry messages. A FAQ entry should follow adoption, when collaborators have a settled contract to follow.

## Abuse limits apply to attempts and new writes

Retain the current creation quotas in [`convex/lib/rateLimits.ts`](../../convex/lib/rateLimits.ts): rapid entry 120 per member/hour and 500 globally/hour; historical claims and occupancy sets each 240 per member/hour and 1,000 globally/hour. Charge a successful receipt once, including every created component of an atomic request. Add explicit quotas for guided/general submissions and prerequisite creation, including submissions with an empty period array.

Use a separate bounded attempt allowance for committed fresh submissions, successful replays, content conflicts and typed correction refusals. The proposed allowance is 60 authenticated requests/minute/member with a burst of 20, plus a deployment-wide ceiling set from measured capacity. Returning conflicts and correction refusals as values commits their attempt charges; malformed requests and thrown validation refusals remain uncharged. Payload, segment-count, string-length, source, role and country bounds apply before expensive work. Fresh submissions also consume the applicable member/global creation quotas. Keep receipts private and exclude canonical evidence, raw authentication tokens and content digests from public telemetry.

## Four rulings requested from JB

The four recommendations below await JB's decision.

- **R-I1 Atomic entry points.** Question: should a send commit prerequisites and evidence in one mutation? Options: (a) use the atomic rapid and guided entry points specified above; (b) retain the current multi-call flows with their prerequisite retry gaps. Recommended (a), because the transaction can commit the request's source, task, revision, draft and evidence together.
- **R-I2 Correction scope.** Question: which edits may a fresh attempt make after a content conflict? Options: (a) observation fields only, returning `correction_required` for candidate name, address, locality, pin, location assertion or link edits and asking the member to nominate a separate revision issue through `tasks:createIssueTask` with `sourceTaskId` and a `locationAssertion`; (b) also support candidate edits through a new attributed candidate-correction write, including reciprocal-link changes. Recommended (a), because the existing correction path supports observation fields; option (b) requires a new write contract.
- **R-I3 Legacy behaviour.** Question: how should a legacy hit respond? Options: (a) today's deduped result in the new shape with `legacy_unverified: true`; (b) refuse pending member reconciliation. Recommended (a), because existing submissions remain recoverable and the marker states the equality limit.
- **R-I4 Attempt allowance.** Question: should the new contract use the proposed member attempt limit? Options: (a) 60 requests/minute/member with a burst of 20; (b) a different allowance specified by JB. Recommended (a) as the initial setting, because replays and conflicts consume backend capacity even when creation quotas remain unchanged.
