# Correction to the 2026-09-10 agent research pilot

The original [pilot report](pilot-2026-09-10.md) and its dossier and validation JSON files remain a historical record. This correction follows the code review of PR #107 on 2026-09-11. It changes the interpretation of the reported validation results. Verification for this amendment used offline fixtures and saved outputs.

## Locator accounting

The original `locator_validity_rate` calculated the complement of observed HTTP 404/410 responses. It counted blocked, failed, and unattempted requests positively. Therefore, the reported validity rate and claim of zero hallucinated locators are unsupported. The saved run recorded zero HTTP 404/410 locators; unresolved responses leave existence unestablished. Reader totals sum distinct locators within each dossier. The same URL may therefore contribute to several dossiers or readers.

Validator v2 replaces validity with a partition: verified, dead, and unresolved. Verified means readable content or a history version verified against the matching OSM object. Dead means an observed HTTP 404/410 response. Unresolved includes blocked, failed, skipped, and otherwise unverified requests. These categories sum to the number of distinct locators in a dossier. Blocked requests are a subset of unresolved requests.

## Quotation and location interpretation

Quotation matching measures textual occurrence after normalisation; partial matching uses word bigrams. Semantic support and verbatim transcription require separate assessment. The quotation-match denominator contains fetched text with quoted support. A miss within that denominator concerns a checked passage; PDFs and inaccessible pages are recorded separately. The original brief's explanation of those misses was incorrect.

Candidate coordinates close to the seed or OSM centroid demonstrate consistency with that reference. Readers using the same OSM geometry provide dependent evidence about location. Independent location accuracy requires a separate source or adjudicated reference.

## Agreement and OSM verification

The original date comparator matched any year in the dates or claim text. It could equate a worship-end claim with a different date because both descriptions mentioned a sale year. It also kept the first claim of each type, discarding competing readings from the calculation. Those defects prevent interpreting the original agreement rate as a validated measure of agreement on historical events.

Agreement v2 retains every claim, compares explicit event bounds at matching granularity, and escalates conflicting, missing, or incomparable readings. Year-only bounds retain the pilot's one-year tolerance; month and day values require matching values. Broad bounds must match at both endpoints within the relevant tolerance. Text overlap remains a triage heuristic. Review must establish whether claims concern the same site, event, and period; common claim types alone leave those questions open.

The original OSM history shortcut matched the version number against the seed object's history and omitted the locator's object identity. Validator v2 requires the object type and identifier to match. Version-chain checks establish changeset and year consistency; tag interpretation and precise timestamps require their own checks.

## Operational boundary

Regression tests cover these failures and the validator's public-address restrictions. HTTP connections validate DNS answers, pin the selected numeric destination, retain TLS hostname verification, and recheck each redirect. Unknown robots policies suspend fetching. These controls govern the deterministic validator; vendor reader tools have their own access boundaries.

This remains a manually triggered research pilot. Model quality, comprehensive privacy filtering, cultural-sensitivity routing, production cost controls, and automated reviewer-task creation require further evaluation or implementation. Comparative evaluation of Luna and local models remains pending. The approved handoff design is reviewer acceptance into a transparent export queue, explicit PI batch release, and governed `pow` processing, with return to review before acceptance. The current per-item PI backend remains operational until that replacement is implemented.
